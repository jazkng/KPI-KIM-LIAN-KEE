# V1 生产环境 · 紧急安全整改计划

- 日期：2026-10-12
- 状态：**计划草案**。每一张变更单（CHG）都需要负责人**单独批准**后才能执行。本文件本身不改动任何生产系统。
- 背景与风险评估：见 [`2026-10-12-security-remediation-plan.md`](2026-10-12-security-remediation-plan.md) 第一部分。
- 约束：
  - 继续只用一个 Firebase 项目。
  - **不新建数据库实例**。
  - 两个 V1 网址保持营业。
  - 每项变更必须有回滚方案。

## 优先顺序

| 顺序 | 变更单 | 主题 | 阻挡的风险 | 需要改代码 |
| --- | --- | --- | --- | --- |
| 0 | CHG-00 | 只读核实 | — | 否 |
| 1 | CHG-01 | **备份**（PITR + 每日备份 + 立即导出一次） | 数据被删、被改后无法恢复 | 否 |
| 2 | CHG-02 | Gemini 用量上限与预算提醒 | 费用被滥用 | 否 |
| 3 | CHG-03 | **发票扫描代理加锁** | 公网可删除或归档 Drive 发票 | 是（小） |
| 4 | CHG-04 | 「初始化系统」防误触 | 误覆盖员工资料 | 是（小） |
| 5 | CHG-05 | **服务端 PIN 验证 + 登录身份** | 伪造登录、外部直接读写（第一步） | 是（中） |
| 6 | CHG-06 | **收紧 Firestore Rules** | 匿名身份读写整个数据库 | 只改 Rules |
| 7 | CHG-07 | **员工 PIN 重设与哈希存储** | 已外泄的 PIN 继续有效 | 是（中） |

CHG-01 和 CHG-02 不改代码，批准后当天就可以完成。CHG-03 和 CHG-04 可以合并为同一次 V1 部署。

## 共同执行规则

1. **一次只做一张变更单。** 上一张验证完成、观察至少一个营业日后，再做下一张。
2. 在**非营业时段**执行，具体时间由负责人指定。执行前先确认 CHG-01 的备份是最新的。
3. 改代码的变更：
   - 先在 `hotfix/v1-security-*` 分支开发；
   - 用 Emulator 测试，CI 全绿，并由另一个 AI 审核；
   - 负责人批准后，在 AI Studio 套用并部署。
   - 两个 V1 部署都要套用，并记录各自的部署版本。
4. 每次执行后，在本文件末尾的「执行记录」中填写：日期、执行人、版本或 Commit、验证结果、是否回滚。
5. 任何一步出现异常，**先回滚，再分析**。

## CHG-00 · 只读核实（负责人操作，不改任何东西）

- **目的**：确认风险是否真实存在于生产环境，并确定 CHG-03 和 CHG-05 的前提条件。
- **步骤**：
  1. Firebase Console → Firestore → Rules：截图正式规则，对照仓库中的 `firestore.rules`。
  2. Authentication → Sign-in method：Anonymous 是否已启用；Users 页的匿名用户大约有多少。
  3. AI Studio：两个 V1 App 的 Secrets 名称中是否有 `INTERNAL_API_KEY`、`GEMINI_API_KEY`（只看名称）；两个 App 是否连接同一个 Firebase 项目。
  4. Cloud Run → ap-ai-service → Logs：最近 30 天是否有异常的 `delete-pending`、`commit-bill` 请求。
  5. GCP → IAM：AI Studio 部署所用的 Cloud Run 服务账号是哪一个，能否调整权限（决定 CHG-05 的做法）。
- **回滚**：不适用。

## CHG-01 · 备份（第一优先）

- **目的**：在做任何其他变更之前，确保数据能恢复到任意时间点。
- **内容**：
  1. **启用 PITR（时间点恢复）**：对现有 `(default)` 数据库开启，可回溯最近 7 天任意一分钟的数据。
     `gcloud firestore databases update --database='(default)' --enable-pitr`
  2. **建立每日备份计划**：保留 14 天。
     `gcloud firestore backups schedules create --database='(default)' --recurrence=daily --retention=14d`
  3. **立即做一次完整导出**：导出到同一项目中的 Cloud Storage bucket。
     `gcloud firestore export gs://<备份bucket>/manual-2026-10-xx`
     - bucket 是存储空间，**不是数据库实例**；
     - 建议设置为只有负责人可访问，并开启对象保留期，防止误删。
- **不需要新数据库的恢复方式（事故发生时使用）**：
  - **PITR**：
    - 以过去某个时间点导出：`gcloud firestore export --snapshot-time=<时间>`；
    - 再把受影响的集合导入回 `(default)`：`gcloud firestore import --collection-ids=...`。
    - 导入会覆盖同 ID 文件，不会删除多出来的文件。
  - **手动导出**：用同样的 `import` 方式恢复。
  - ⚠️ 「从备份计划恢复」在 Firestore 中**一定会建立一个新数据库**。按目前的约束，这种方式只作为最后手段，事故发生时另行批准。
- **恢复演练（不建新数据库）**：
  - 把导出文件下载到负责人自己的电脑，导入本机 Emulator 核对员工、日结、账单的笔数。
  - 这一步在负责人电脑上进行，不在 CI 或云端，完成后删除本地副本，因为里面有 PIN 等敏感资料。
  - 能否直接导入 Emulator 需要先验证；如果不行，改为只核对导出文件的完整性与大小。
- **验证**：
  - Console 中 PITR 显示「已启用」；
  - 备份计划列表中有每日计划；
  - 第一份每日备份成功；
  - 手动导出的 bucket 中有完整文件。
- **回滚**：关闭 PITR（`--no-enable-pitr`）、删除备份计划。这些操作对现有数据没有任何影响。
- **对员工的影响**：无。
- **费用**：按存储量计费。开启前请用 GCP 价格计算器估算；小型数据库通常很低。

## CHG-02 · Gemini 用量上限与预算提醒

- **目的**：限制发票扫描代理和 `/api/gemini/*` 被滥用时的费用。
- **步骤**：
  - GCP → APIs & Services → Gemini API → Quotas：为 V1 所用的 Key 设置每日请求上限，建议为平时用量的 2–3 倍。
  - Billing → Budgets：设置月预算，并在 50%、90%、100% 时发电邮提醒。
- **验证**：配额页面显示新的上限；预算列表中有新预算。
- **回滚**：调回原来的配额，或删除预算。
- **对员工的影响**：只有超过上限时，AI 功能当天会暂停。

## CHG-03 · 发票扫描代理加锁（V1 代码）

- **目的**：关闭「任何人都能通过 V1 网址操作 Drive 发票」的漏洞。
- **改动**（`server.ts` 中的 `/api/ap-ai`）：
  1. 只放行前端实际调用的路径：`GET /api/scan-pending`、`POST /api/commit-bill`、`POST /api/hold-pending`、`POST /api/delete-pending`、`GET /health`。其余一律返回 404。
  2. 要求请求头 `X-AP-Access` 与服务端 Secret `AP_ACCESS_CODE` 相符，使用常数时间比较。
     - **未设置该 Secret 时拒绝所有请求**，确保不会因为漏配而放行。
  3. 前端「应付账款」第一次使用时，请老板或会计输入访问码，保存在该设备。
- **前提**：在两个 V1 App 的 Secrets 中加入 `AP_ACCESS_CODE`（随机生成，至少 32 位）。
- **验证**：
  - 带正确访问码 → 扫描、提交、搁置、删除功能正常；
  - 不带访问码 → 401；
  - 访问不在白名单的路径 → 404。
- **回滚**：在 AI Studio 重新部署上一版。不涉及数据变更。
- **对员工的影响**：只影响使用应付账款的人；每台设备输入一次访问码。
- **后续**：完成 CHG-05 后，改为验证登录身份，取消访问码。

## CHG-04 · 「初始化系统」防误触（V1 代码）

- **目的**：避免网络故障时员工误按初始化按钮，覆盖正式员工资料。
- **改动**（`components/Login.tsx`）：
  - 只有**成功读取**到 0 位员工时，才显示初始化按钮；
  - 读取失败时显示「连接失败，请重试」和重试按钮。
- **验证**：在 Emulator 中断开网络，或让读取失败 → 不出现初始化按钮。
- **回滚**：重新部署上一版。
- **对员工的影响**：无。

## CHG-05 · 服务端 PIN 验证 + 登录身份（V1 代码）

- **目的**：
  - 登录不再在浏览器中比对 PIN，浏览器也不再下载 PIN；
  - 每位员工登录后都有一个带角色信息的 Firebase 身份（Custom Token claims）。
  - 这是 CHG-06 的前提，同时修好「伪造登录状态」的漏洞。
- **改动**：
  - 新接口：`/api/auth/roster`（不含 PIN）、`/api/auth/login`、`/api/auth/device-login`、`/api/auth/change-pin`；
  - 登录页和 App 启动流程改为以 Firebase 登录状态为准。
  - 详细设计见安全整改方案的 E2。
- **前提**：
  - 由 CHG-00 第 5 项确定服务账号能否签发 Custom Token。
  - 如果 AI Studio 的服务账号无法调整，就在同一 GCP 项目中新增独立小型 Cloud Run 服务 `klk-auth`（不是数据库实例），这需要单独批准。
- **上线顺序**：
  1. 两个 V1 部署都上线新登录（此时 Rules 未变，旧设备仍可正常使用）；
  2. 观察 2–3 个营业日；
  3. 确认所有设备都已用新方式登录过。
- **验证**：
  - 老板、管理层、员工、只读、专用设备五类账号都能登录，并进入正确页面；
  - 浏览器 Network 中看不到任何 PIN；
  - 伪造 localStorage 后会被退回登录页。
- **回滚**：重新部署上一版。新接口不改变数据结构，旧版仍可直接运行。
- **对员工的影响**：PIN 不变；每台设备需要重新登录一次。

## CHG-06 · 收紧 Firestore Rules（只改 Rules）

- **目的**：只有经过 CHG-05 登录的员工或设备才能读写；匿名身份一律拒绝。
- **前提**：CHG-05 已在**两个** V1 部署上线并稳定，因为两个部署共用同一套 Rules。
- **步骤**：
  1. 在仓库中修改 `firestore.rules`，把 `tests/rules` 中的 KNOWN GAP 测试改为 `assertFails`；
  2. 补齐专用设备所需集合的测试，Emulator 测试全部通过；
  3. 负责人在 Firebase Console 发布。
- **验证**：
  - 各类账号的常用流程正常：日结、打卡、库存、排队屏、厨房提醒；
  - 用匿名身份读取 `employees` → 被拒绝。
- **回滚**：Firebase Console → Rules → 历史版本 → 恢复上一版。一键完成，即时生效，不影响数据。
- **对员工的影响**：无。如果有遗漏的功能被挡住，立即回滚后补测试。

## CHG-07 · 员工 PIN 重设与哈希存储（V1 代码 + 数据迁移）

- **目的**：在 CHG-06 之前，员工 PIN 对外公开可读，**必须视为已经外泄**。这一步让所有人换新 PIN，并以哈希方式保存。
- **改动**：
  1. 新的 PIN 只以哈希形式存入 `employee_secrets/{id}`。Rules 设为客户端完全不可访问。这是一个**集合**，不是新的数据库实例。
  2. 员工下次登录时强制更改 PIN，新 PIN 直接以哈希保存。
  3. 专用设备的 PIN 也全部重设。
  4. 全部员工完成更换后，再删除 `employees` 中的旧 `pin` 字段。**删除前另做一次 CHG-01 手动导出。**
  5. 取消默认 PIN `8888` / `0000`。
- **验证**：
  - 所有在职员工都已更换 PIN；
  - `employees` 文件中已没有 `pin` 字段；
  - 用旧 PIN 无法登录。
- **回滚**：
  - 第 1–3 步不删除任何旧数据，可以重新部署上一版回退。
  - 第 4 步（删除旧字段）不可逆，只能从 CHG-01 的导出中恢复，所以必须单独批准，而且放在最后。
- **对员工的影响**：每人更换一次 PIN，约 1 分钟。
