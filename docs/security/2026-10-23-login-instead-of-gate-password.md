# 登录后免预览站密码 —— 设计说明

> 状态：**负责人已批准（2026-10-23）**，已实施，等负责人设定权限后开启。
> 负责人回答：1. 登录记录到期后重新输入员工 PIN（有效期采用建议的 30 天）；2. 选 (b) 登录页不显示名单，改输入员工号；3. 同意打开服务端登录。
> 日期：2026-10-23
> 负责人要求：「登入后免密码」—— 员工用自己的员工号 + PIN 登录后，不用再输入共用的预览站密码。

## 1. 现在的情况
- `epr.kimliankee.app` / `dev.kimliankee.app` 打开时，浏览器先问「预览站密码」（全员共用一个），通过后才看到登录页，再输入员工 PIN。
- 服务端登录（CHG-05，员工 PIN 在服务端比对、存哈希）**程序已经做好，但预览站还没打开**（`AUTH_SERVER_ENABLED` 未设定）。现在用的仍是和 V1 一样的前端比对 PIN。

## 2. 做法
**先打开服务端登录，再让「登录成功」代替预览站密码。**

1. **登录页不用密码就能打开**：门禁放行以下内容，其余一律要密码或登录记录：
   - 页面本身（`index.html`、`/assets/*`、图标、`manifest`、`sw.js`）；
   - 登录用的接口：`/api/auth/config`、`/api/auth/login`、`/api/auth/boss-login`、`/api/auth/change-pin`、`/api/auth/device-login`，以及登录页名单（见第 4 节问题 2）。
2. **登录成功 → 服务端发一张「登录记录」**（浏览器 Cookie）：
   - `HttpOnly`、`Secure`、`SameSite=Lax`，网页程序读不到；
   - 内容只有员工号、到期时间、`AUTH_EPOCH`，用服务端金钥签名，改不了也伪造不了；
   - 有效期 30 天（见问题 1）。期间打开网页不会再问任何密码，只要 App 本身还记得登录。
3. **有登录记录 = 等同输入过预览站密码**：AI 顾问、发票扫描、推送等接口照常可用。
4. **登出、改 PIN、负责人提高 `AUTH_EPOCH`** → 登录记录失效。
5. **预览站密码保留**，当作负责人的后备入口（例如服务端登录出问题时），也供 Cloud Scheduler 以外的维护使用。

## 3. 打开服务端登录会带来的变化（员工会感受到）
- **PIN 是 0000 或没有设 PIN 的人**：第一次登录必须改成 6 位数字的新 PIN（不能全同一数字，不能 123456 / 654321）。
- 新 PIN 会**同步写回** `employees.pin`（过渡期设定 `MIRROR_LEGACY_PIN`），所以员工在 V1 也用新 PIN，V1 照常运作。
- 同一员工 + 同一网络 15 分钟内错 5 次锁 15 分钟；老板入口锁 30 分钟。
- 厨房屏等设备：用设备户口登录（CHG-05b 已完成），同样拿到登录记录。

## 4. 要负责人决定
1. **登录记录有效期**：30 天（建议），还是 7 天？到期后重新输入员工 PIN（不是预览站密码）。
2. **登录页的员工名单**：现在登录页列出全部员工（姓名、职位、头像，不含 PIN 和薪资），让人点选。免密码后，**任何知道网址的人都看得到这份名单**。
   - (a) 照旧显示名单（方便，名单公开）；
   - (b) 改成输入员工号，不显示名单（建议，较安全；员工要记自己的员工号）。
3. **同意打开服务端登录**（第 3 节的 PIN 规则会生效）。

## 5. 风险与说明
- 页面程序本身变成公开可下载。里面的 Firebase 设定本来就是公开设定，V1 的 AI Studio 网址早已公开同一份，不增加资料库风险。资料库的真正风险（规则允许任何登录身份读写）仍要靠 CHG-06 收紧规则解决，与本项无关。
- 登录接口变成公开可试 PIN：已有限次与锁定；另加「每个员工不论 IP，1 小时内错 20 次即锁定」，防止换 IP 猜 PIN。
- AI、发票扫描等花钱的接口仍然要登录记录或预览站密码，陌生人用不到。

## 6. 资料与 V1 兼容
- 不新增或改动资料库集合与字段（登录记录只在浏览器 Cookie，不写资料库）。
- 服务端登录用到的 `employee_secrets`、`auth_rate_limits` 等是 CHG-05a 已批准的新集合。
- V1 不受影响：V1 不经过这个服务端；新 PIN 同步写回 `employees.pin`，V1 照常比对。

## 7. 上线步骤与回滚
1. 负责人一次性设定（Cloud Shell，约 5 分钟）：运行用服务账号加上签发登录凭证与读取资料库的权限；新增签名用的 Secret。（我会写成脚本。）
2. 部署设定加 `AUTH_SERVER_ENABLED=true`。
3. 负责人先在预览站用自己的账号试：登录、改 PIN、关掉浏览器再开不问密码、登出后要重新登录。
4. **回滚**：把 `AUTH_SERVER_ENABLED` 拿掉重新部署 → 回到「先输入预览站密码、前端比对 PIN」的现状。已改的新 PIN 已同步写回 `employees.pin`，员工继续用新 PIN 即可。

## 8. 测试
- 单元测试：登录记录的签名、到期、篡改、`AUTH_EPOCH` 失效；门禁放行清单（页面与登录接口放行，其余没有记录一律 401）。
- Emulator：未登录打开 → 看到登录页、不问密码；登录 → AI 接口可用；登出 → AI 接口 401；伪造 Cookie → 401。
- 部署的冒烟测试改为：未登录访问 `/api/gemini/chat` 等接口必须 401（取代现在「首页必须 401」）。

## 9. 实施记录（2026-10-23）
- `server/auth/sessionCookie.ts`：登录记录的签名、验证、放行清单（纯函数，有单元测试）。签名金钥用 `SESSION_SECRET`，没设就由预览站密码导出。
- `server.ts`：服务端登录开通时，门禁改为「页面与登录接口公开，其余 /api 要登录记录或预览站密码」，不主动弹出密码框；新增 `GET /api/auth/session`、`POST /api/auth/logout`。
- 登录、老板登录、改 PIN、设备登录成功时发登录记录；同一员工不论 IP 1 小时错 20 次锁 1 小时。
- 登录页改用 `/api/auth/branding`（只有 Logo），员工名单接口要登录。
- App 恢复登录时检查登录记录，到期就回登录页重新输入 PIN。
- 部署：GitHub 变量 `AUTH_SERVER_ENABLED=true` 才开启；冒烟测试改为「未登录访问 `/api/auth/session` 必须 401」（两种模式都适用）。
- 负责人一次性权限设定：`docs/deploy/enable-server-login.sh`。
