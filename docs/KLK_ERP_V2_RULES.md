# 金莲记 · 御膳智控 ERP V2
## Claude Code + Codex 联合开发与部署总规范

**文档版本：** 1.0  
**日期：** 2026-10-12  
**项目：** KPI-KIM-LIAN-KEE  
**GitHub：** https://github.com/jazkng/KPI-KIM-LIAN-KEE  
**适用对象：** Claude Code（CC）、OpenAI Codex 及所有参与者

> 本文是开发与部署工作规范。任何会影响正式系统、正式数据、域名或部署的操作，必须先说明风险并取得负责人明确批准。

## 1. 核心目标

1. 在不影响现有 ERP V1 营业的前提下，全面开发 ERP V2。
2. Claude Code 与 Codex 协作开发、交叉审核并持续优化彼此的代码。
3. GitHub 作为未来唯一正式代码来源，不再以 AI Studio 直接修改正式版代码。
4. 完成 V2 后进行受控的整体发布；在此之前不更新 V1 正式部署。
5. **继续使用现有一个 Firebase 云端项目**，保留历史数据、员工账号、财务与库存记录，不另建第二个云端 Firebase 项目。
6. 提供 V2 独立预览网址，让负责人随时查看已测试的更新。

- 未经批准，不得修改 Cloudflare DNS、生产域名、旧 AI Studio 部署、生产后端或正式付款设置。

## 3. GitHub 分支与协作

- `main`：当前正式版本的**代码基准**，开发 V2 期间冻结；不代表该分支已自动控制 AI Studio 正式部署。
- `develop-v2`：V2 整合分支，经审核合并后用于更新 V2 预览部署。
- `claude/<feature>`：Claude Code 每项独立工作所用功能分支。
- `codex/<feature>`：Codex 每项独立工作所用功能分支。

工作流程：
1. 开始工作前，先拉取最新远端状态、查看当前分支及未提交更改，确认最近 AI Studio 同步确实已进入 GitHub。
2. 从最新 `develop-v2` 建立独立功能分支，避免 Claude 与 Codex 直接并发写同一分支/共享工作目录。
3. 在功能分支开发、运行静态检查、构建和相关测试。
4. 通过 Pull Request（PR）提交至 `develop-v2`，说明改动、影响范围、迁移风险、测试证据。
5. 另一位 AI 交叉审核，开发者修复问题；自动检查通过后才合并。
6. 合并后由单独的 V2 预览部署流程发布 `dev.kimliankee.app`，记录 Commit SHA、部署结果和回滚版本。
7. **未经负责人明确批准，绝不可合并到 `main`、发布 V2 正式版或修改 V1。**

严格禁止：`git push --force` 覆盖共享分支、跳过代码审核、擅自更改分支保护、泄露密钥、用任何 AI 自动将变更写入生产环境。

## 4. Claude Code 与 Codex 分工、互相升级

**Claude Code 主责：** 业务逻辑、后端/API、权限、数据库兼容性、ERP 模块联动、复杂问题修复。

**Codex 主责：** 手机与电脑 UI/UX、前端交互、可用性、自动化测试、性能、安全及代码审查。

这不是独占范围。双方可以提出和实施对方领域的改进，但要在自己的功能分支内进行，并通过 PR 交流。反向审核同样适用：Claude 开发 → Codex 检查；Codex 开发 → Claude 检查。

重大改动（数据模型、访问权限、资金逻辑、自动扣库存、部署架构等）必须先形成设计说明，让负责人批准后再修改。

## 5. Firebase：一个云端项目，保留多年历史

- 保留现有 Firebase Project；不要创建第二个云端 Firebase 项目。
- Firebase 可能涉及 Firestore、Authentication、Storage 与 Security Rules，须先核实项目实际使用的服务。
- **禁止 V2 测试代码对生产 Firebase 读写真实业务资料，尤其禁止测试写入、删除或批量改动。** 使用 Firebase Local Emulator Suite、Mock、测试 fixture 等隔离方式。
- 不准为方便测试而降低 Firebase Security Rules、开放匿名写入、给客户端管理员权限。
- 正式 Firestore Collection、字段、索引、Rules、Cloud Functions、用户权限与生产数据的变更都须先做影响评估；涉及破坏性或全局变更必须单独获批。
- 采用向后兼容的数据变更：优先新增可选字段和渐进迁移，保留老字段读取及旧版使用能力，避免 V1/V2 共用后端时发生兼容冲突。
- 原始交易、历史日结、成本计算依据、审计日志不得被新公式无声改写；财务历史报表必须可追溯至原始记录和适用规则版本。
- 正式上线前建立可靠的备份与恢复演练，并制定数据迁移和回滚程序。**备份必须验证可恢复，不是只看到备份任务成功。**
- 不在源码、日志、PR、聊天中暴露 API 密钥、服务账号 JSON、访问令牌或其他 Secrets。Firebase Web API Key 并非独立授权机制，也不能替代 Security Rules。

## 6. 部署、CI/CD 和正式切换

### V2 预览
- 先核实 GitHub Actions、AI Studio、Cloud Run（或其他托管）是否已经关联现有 V1；**未经核查不得开启自动部署**。
- CI 至少执行 TypeScript 类型检查、生产构建、关键功能测试及基础依赖/密钥检查。
- 仅在 `develop-v2` 合并并通过检查后部署 V2 预览；预览失败不影响 V1。
- 预览 API 和数据库操作必须默认隔离，不使用生产数据做破坏性测试。

### V2 正式发布
1. 盘点 V1 两个在用网址各自的代码版本、登录流程、后端、Firebase Project ID 和生产访问流量，不靠网页标题推断它们相同。
2. 比较并保留两个 V1 可能独有的功能与配置。
3. 确定 V2 功能范围，完成端到端验证，包括权限、员工登录、订单、库存、采购、薪资、日结、财务、历史数据、PDF/打印和移动端。
4. 备份生产数据库，演练恢复，完成迁移评审；安排低风险发布窗口。
5. 负责人明确批准后，才发布到 `erp.kimliankee.app`，设置 Cloudflare DNS 与 HTTPS。
6. 切换期间继续监控错误率、业务数据、订单流与权限。保留旧版可回退的代码/部署版本。若数据库迁移不可逆，需单独准备兼容和数据恢复方案，不能假设回退代码即可回退数据。
7. 确认 V2 稳定并由负责人同意后，才考虑逐步停用旧 AI Studio 入口。

## 7. 代码质量与安全底线

- 移动端优先，兼顾桌面使用；避免操作复杂化。
- 老板、管理层、部门、员工等各角色权限必须由后端/数据库规则真正执行，不能仅隐藏前端按钮。
- 财务金额采用一致且可审计的计算方式；重复提交、断网重试、并发库存/订单变化要有保护。
- 新功能不应破坏旧功能；每次改动附必要测试。
- 严格区分 Mock 数据与真实营业数据；测试消息、假订单、假交易不能进入生产账目。
- 不允许声称「已测试」却未实际运行；说明实际测试命令和结果。

## 8. 每项任务的交付报告

每次开发/审核后报告：
- 任务目标、完成的功能和未完成事项
- GitHub 分支、Commit SHA、PR 链接与主要修改文件
- 执行的 TypeScript/Build/测试命令和结果
- 数据库/权限/部署影响分析
- 是否涉及 V1 生产环境（正常应为**否**）
- 发现的问题、风险、需要负责人批准的操作及下一步建议
