# 稳定期开发与部署提速（2026-10-24，负责人已批准）

负责人在本次对话批准执行提速建议。先实施重复构建和部署任务合并，不启用按文件跳过测试。

## 改动与验证边界

1. CI 用虚构非 demo Firebase 配置完成一次 Vite 构建及服务端 esbuild，再直接检查 dist 的首屏体积和按需模块。不会连接正式 Firebase；原先缺配置构建及体积脚本各构建一次的重复工作合为一次。
2. 合并 develop-v2 后，候选部署、候选门禁检查、指定 revision 的流量切换及切换后检查在同一 job 内完成，省掉第二次 runner／认证／gcloud 安装。
3. 手动 deploy 仍只建 0% 流量候选；promote／rollback 独立入口保留。自动切换后门禁失败仍切回记录的上一版；curl 网络失败也按失败处理。
4. 所有类型、单元、Emulator、密钥扫描和体积检查保留。不复用配置不同的 CI dist 到正式镜像；Docker 仍以实际公开配置独立构建。
5. 稳定期由负责人完成完整业务操作和手机／iOS 体验验收。AI 完成改动所需自动验证、独立复核、部署状态及必要入口／安全检查；除非修复需要，不重复全模块截图和人工操作。

数据库、权限、V1、DNS、正式站发布流程均不变。仅 develop-v2 自动部署 dev；epr 仍须负责人说「发布」。如有问题，revert 本 PR 即恢复原有流水线，无数据回滚。

以实际 GitHub Actions 的总耗时比较效果，目标不是承诺。上次基准 run 40051342990：4分58秒。缓存冷热和 runner 排队会影响比较结果。

## 本机验证记录

`npm run lint`、515 项单元测试、38 项 Emulator 测试、`npm run build`、`npm run build:ci` 均通过。实际切换后脚本使用本地 gcloud/curl mock 执行：401 成功不回滚、500 失败回滚、curl 网络失败回滚；缺 Firebase 模块的裁剪产物被体积检查拒绝。独立 AI 复核无合并阻碍。
