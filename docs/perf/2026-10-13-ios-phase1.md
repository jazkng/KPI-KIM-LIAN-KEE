# iOS 性能 · 第一阶段：首屏程序拆分（Issue #8 P0）

- 日期：2026-10-13
- 分支：`claude/v2-ios-perf` → `develop-v2`

## 1. 根本原因

正式构建会把**所有**仪表板与功能模块打包进同一个主程序 `index-*.js`：

| 项目 | 大小 |
| --- | --- |
| 主程序（压缩后） | 4,043 KB |
| 主程序（gzip 后） | 1,071 KB |
| 打开登录画面前必须下载的 JS（主程序 + React + Firebase） | 约 5.0 MB |

iPhone 和 iPad 的 Safari 必须先把这些全部下载、解析、执行完，才看得到登录画面。

主程序中最大的部分如下（单位：压缩后 KB）：

| 模块 | 大小 |
| --- | --- |
| recharts | 278 |
| FinancialReport | 276 |
| HRPayroll | 152 |
| AccountsPayableModule | 121 |
| HRProfiles | 117 |
| SettlementModule | 94 |
| SupplierModule | 87 |
| RecurringBillsModule | 86 |
| AttendanceConsole | 81 |
| staffTranslations | 80 |
| InventoryModule | 78 |

这些模块在登录画面完全用不到。

> ⚠️ **量测陷阱**：在没有 Firebase 配置的环境构建时，Rollup 会把整个 App 当成「执行不到」而删掉，主程序只剩约 280 KB，看起来很小。量测和 CI 检查都必须用「假的非 demo 配置」构建，`scripts/perf/check-bundle-budget.mjs` 已处理这一点。

## 2. 改动

- **`components/lazyModules.tsx`**
  - 4 个仪表板、管理层入口、专用设备入口、4 个弹窗和 24 个功能模块，改为**用到才下载**（`React.lazy`）。
  - 组件名称与 props 类型不变，`App.tsx` 和各仪表板只改了 import 来源。
  - **模块下载失败时**（例如部署了新版本、页面还是旧版），自动重新载入一次以取得新版。60 秒内不重复，避免断网时不停重载。
- **`server.ts`**：不存在的 `/assets/*` 资源回 **404**，不再回首页 HTML。
  - 以前旧版页面请求已被替换的模块时，会拿到 HTML 当成 JS 执行而出错。
  - Service Worker 还会把这份 HTML 缓存在 `.js` 的网址下，之后一直出错。
- **CI 新增「首屏 JS 体积检查」**（`npm run perf:budget`）：
  - 主程序超过 350 KB 即失败；
  - 7 个大型模块（`FinancialReport`、`HRSystem`、`AccountsPayableModule`、`SettlementModule`、`BossDashboard`、`StaffDashboard`、`ManagementPortal`）若被打回主程序，也会失败。
  - 已验证：对拆分前的 `develop-v2` 执行时会失败（主程序 3,948 KB、7 个模块全部未拆）。

登录安全、Firestore 读写、历史数据都没有改动。

## 3. 量测结果（可重复）

**条件**：
- Chromium 模拟 iPhone 13 画面；
- CPU 降速 4 倍；
- 4G 网络（下行 9 Mbps、上行 3 Mbps、RTT 40ms）；
- 连接本机 Emulator；
- 每个版本量 3 次，取中位数。

**脚本**：`scripts/perf/measure-mobile.cjs`（使用方法见文件开头）。

| 指标 | 拆分前（develop-v2） | 拆分后（本 PR） |
| --- | --- | --- |
| 打开网址 → 登录画面可输入 | **6.8 s** | **2.7 s** |
| 登录画面前下载的 JS | 4,912 KB | 1,156 KB |
| 打开网址 → 老板首页可用（含输入 PIN 与员工资料载入） | **9.2 s** | **5.0 s** |
| 页面错误 | 0 | 0 |

另一次独立量测：拆分前 6.7 / 11.0 s，拆分后 2.6 / 4.9 s。

> 这是模拟条件下的相对比较，不等于实机秒数。实机验证请在预览站部署后，用 iPhone / iPad Safari 实际打开。

## 5. 下一步（第二阶段）

- **Firestore 读取**：
  - 盘点登录后各首页的查询与监听（`onSnapshot`），找出重复请求、没有 `limit` 的整集合读取、一打开就读取的大集合；
  - 改为分页或按需读取，并沿用现有的 `DataManager` 快取。
- **Firebase SDK**：本身 790 KB，是首屏剩余最大的部分，评估能否延后载入 Auth 以外的部分。
- **实机验证**：预览站部署后，请在出问题的 iPhone / iPad 机型上实测，并回报型号、iOS 版本和网络环境。
