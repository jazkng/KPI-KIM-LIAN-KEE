# 设计说明：管理层派任务给员工 + 完成后验收审批

> 状态：**待负责人批准**。批准前不写代码，也不建资料集合。
> 依据：CLAUDE.md「数据模型、权限的改动：先写设计说明并获负责人批准」。

## 1. 要解决的问题
- 管理层交代员工做事（清洁冷气、整理仓库、补贴标签、跟进客诉……）目前靠口头或 WhatsApp。做了没有、做得好不好、谁做的，都没有记录。
- 系统里现在只有「盘点任务」（`inventory_tasks`）可以指派，而且只能派盘点。
- 目标：管理层**派任务** → 员工**完成并回报**（拍照 / 备注）→ 管理层**验收：通过或退回**。全程可追查。

## 2. 流程
```
管理层派任务 ──▶ 员工收到（员工页「我的任务」，有通知）
                    │ 员工按「开始」（选填）
                    ▼
               员工按「完成」：拍照 / 写备注
                    │
                    ▼
管理层「待我处理」出现「待验收 N」──▶ 通过 ✓（结束）
                                  └─▶ 退回 ✗（写原因，回到员工重做）
到期没完成 ──▶ 管理层看到「逾期 N」，员工看到红色提醒
```

## 3. 派任务时填什么（越少越好）
| 栏位 | 必填 | 说明 |
|---|---|---|
| 做什么 | ✓ | 一句话，例如「清洗 2 号冷气滤网」 |
| 派给谁 | ✓ | 可以选一个或多个员工；也可以选「整个部门」（谁先接谁做） |
| 什么时候前完成 | ✓ | 日期加时间，可以快选「今天收工前」「明天」「本周内」 |
| 要不要拍照 | | 勾选后，员工要拍照才能按完成 |
| 重复 | | 不重复 / 每天 / 每周几 / 每月几号。到时间自动再派一次 |
| 优先 | | 普通 / 紧急（紧急的排最前面、通知更明显） |
| 说明 / 参考照片 | | 选填 |

## 4. 资料设计（新集合，V1 不读不写）
新集合 `staff_tasks`，一个任务一份文件：

```ts
interface StaffTask {
  id: string;
  title: string; note?: string; refPhotoUrl?: string;
  priority: 'NORMAL' | 'URGENT';
  requirePhoto: boolean;
  assigneeIds: string[]; assigneeNames: string[];
  department?: string;              // 派给整个部门时
  dueAt: string;                    // ISO
  createdBy: string; createdByName: string; createdAt: string;
  status: 'OPEN' | 'IN_PROGRESS' | 'SUBMITTED' | 'APPROVED' | 'RETURNED' | 'CANCELLED';
  submittedBy?: string; submittedAt?: string; proofPhotoUrls?: string[]; proofNote?: string;
  reviewedBy?: string; reviewedAt?: string; reviewNote?: string;
  repeat?: { kind: 'DAILY' | 'WEEKLY' | 'MONTHLY'; days?: number[] }; // 重复任务
  seriesId?: string;                // 同一个重复任务的每一次
  history: { at: string; by: string; action: string; note?: string }[];   // 只增不删
}
```

- **不删除**：取消、退回都只改状态，并在 `history` 加一笔。
- **不碰现有资料**：盘点任务（`inventory_tasks`）照旧运作，只在「待我处理」里一起显示数量。
- **重复任务**：只在有人打开管理层页时补派下一次，而且要管理层按确认才生效。不新增后台排程，也不会在打开页面时自动写入。
- **照片**：存 Firebase Storage，路径为 `staff_tasks/{任务id}/…`，跟现有收据照片的做法一样。

## 5. 画面
- **管理层首页「待我处理」**新增三行：
  - 待验收：员工已回报，等你按通过或退回。
  - 逾期：过了期限还没完成。
  - 进行中：已派出、员工还没回报。
- **派任务按钮**：管理层首页顶部加一个「＋ 派任务」，填完第 3 节的表单就送出。
- **验收画面**：显示员工的照片和备注，下方两个大按钮「✓ 通过」「✗ 退回」；退回时必须写原因。
- **员工页「我的任务」**：按期限排序，紧急的排最前面。按「完成」时会要求拍照或写备注；被退回的会显示退回原因。
- **通知**：沿用现有通知中心。派任务时通知员工，员工回报后通知派任务的人，退回或通过后再通知员工。
- **任务记录**：可以按员工、部门、日期查看完成率与逾期次数（只读）。以后也可以拿来当考核参考，但不自动扣分。

## 6. 谁能派、谁能验收
- **L1 / L2**：可以派给任何员工，也可以验收任何任务。
- **L3 部门负责人**：只能派给自己部门的员工，也只能验收自己部门的任务。
- **派任务的人**：一定可以验收自己派出的任务。
- **员工**：只看得到派给自己（或自己部门）的任务，只能回报，不能自己按通过。
- 在员工权限里新增一个可勾选的权限「派任务（TASKS_ASSIGN）」，默认给 L1–L3。这是新增一个选项，旧的权限都不改。
- **现况限制**：V1 的登录与权限只在前端执行（见 `docs/security/`），所以以上规则目前在前端判断。Firestore Rules 要为 `staff_tasks` 加规则（例如员工不能把状态改成 APPROVED）。这属于修改正式 Rules，要另外取得批准。

## 7. 测试与上线
- **单元测试**：
  - 状态流转：OPEN → SUBMITTED → APPROVED / RETURNED；RETURNED → SUBMITTED；不能跳过回报直接通过。
  - 逾期判断。
  - 重复任务的下一次日期。
  - L3 只能派给自己部门。
- **Rules 测试（Emulator）**：员工不能通过自己的任务，也不能改别人的任务。
- **验收方式**：先在 Emulator 测通；再由负责人在预览站用 🧪 测试切换，分别扮演管理层与员工走一遍。不在正式库建立测试任务。
- **分期上线**：
  1. 派任务、回报、验收（含照片）。
  2. 重复任务、任务记录与完成率。

## 8. 回滚
关掉功能开关，画面就不显示。`staff_tasks` 留着不删，也不影响其他资料。
