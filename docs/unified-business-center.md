# 经营中心：界面融合与数据口径整合方案

日期：2026年10月19日。
只读核对的最新 develop-v2：8fec4dbfb0f28bc745f51b24f33941fbdc019487。下列页面与引擎相对本地UI分支基准未改变（已检查相关文件差异）。不连接正式数据库，不声称已复现截图的真实金额。

## 交互稿已经融合

统一老板入口「经营中心」，共享月份，分五个视图：

1. 概况：最近已结算销售、月度营业与成本、利润及提示。
2. 经营日报：销售变化、单数与客单价、人数及人均口径；缺少记录不估算代替。
3. 成本与利润：平台、食材、人工、其他费用、经营利润、Prime Cost、传统账目位置。
4. 现金与账款：实际收付款、净现金变动、期末应付余额，与经营利润明确分开。
5. 数据依据：期间、来源、公式、已确认／暂估／待核对／缺资料。

所有演示视图共用 monthSamples 与 model 结果。演示公式：经营利润=已结算营业额-平台扣款-食材采购成本-人工-其他营运费用。演示成本率分母统一为扣平台前的已结算营业额，平台费用独列且仅扣一次。真实ERP仍须确认并核对口径，未在此更改。

手机先看概况，点开分析；电脑展开组成、趋势和视图。未实现实际凭证、Excel/CSV/PDF导出、财务分红、保本算法；保留现有功能方向，不冒充全部已迁移。

## 只读代码发现

- utils/pnl/engine/pnlEngine.ts 已有 computePnL 纯计算引擎；注释明确全ERP盈亏应统一读取它。
- 引擎规定食材目前按采购金额计，标「采购暂估」，不是库存实际耗用；不以固定比例代替真实金额。
- utils/cockpit/cockpitMetrics.ts 在 engine 存在时使用 E.revenue、E.labour 和 E.netProfit。
- FinancialReport 的传统账目及部分业务发生制人工已经读取 computePnL 结果。不是从零再写一套引擎。

### 仍需核对的并行路径

- components/features/DailyBusinessReportModal.tsx：约339行食材不足时用 revenue*0.35；约364行缺订单时用 revenue/42 推算。日报中仍有单独净利估算。经营中心不应把这些静默后备值当真实值。
- components/features/FinancialReport.tsx：约790–825行，页面成本与净利仍基于本地 analytics 路径；食材、人工率分母是扣平台后的 netRealizedRevenue。与驾驶舱使用 E.revenue 的含义需逐项对齐。
- 同一文件约1553–1564行的 laborDeptAnalysis 又以 proRatedLabor 算 laborMarginSynced；顶部成本健康度读取这一比例，而 Prime Cost 约1120行读取 analytics.costs.totalLabor。存在两条人工展示路径，不能未经同一份资料对账便断言截图差额的唯一原因。
- 同一文件约817–818行，netCashFlow 来自调整后利润减资本支出和分红，尚不能仅凭这个公式证明其是完整实际收付款现金流。需要核查各会计模式和收付款覆盖。

以上是源代码路径证据，不等于已核对正式账目正确与否。用户截图的期间、日结覆盖、会计模式、版本等仍可能不同。

## 正式整合边界

- 先共用筛选上下文：门店、营业日起止、会计口径、截至时间、已结算覆盖。
- 一次读取、一套分类、一次计算，页面和导出读取同一结果；不让每个页面重新分摊人工或扣平台。
- 人工总额与人工率、Prime Cost、利润用同一份人工字段；人数、订单数、客单、人均分开定义。
- 营业额毛额、平台净额、经营利润、现金变动、账款余额分开命名，不能强行做成同一个数字。
- 采购暂估与真实耗用COGS分别定义。今后接入盘点耗用需另做设计与兼容审核。
- 亏损率、评级与目标阈值都要解释依据；资料不足不直接给经营评级。
- 历史更正保留记录，不重写历史交易。共享底层不代表扩大角色权限。

## 对账与验收（正式实现前）

用Mock/Emulator固定输入验证：相同期间所有视图营业额、人工、食材、平台、净利一致；Prime Cost拆分与比例一致；平台只扣一次；预支不重复计薪；兼职与供款一次计入；缺资料不套35%或反推订单；跨期付款不混入当期成本；现金与利润差额有解释；页面与各导出一致；历史月份与月中暂估、期间边界覆盖一致。

本轮没有修改实际ERP应用、计算引擎、报表、数据库或部署；仅本地交互稿与设计记录更新。正式计算路径调整需要负责人审阅方案后按项目规则开发、交叉审核和完整测试，不能直接以交互稿替代。
